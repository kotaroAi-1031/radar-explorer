# Generative UI の方式

## 原則

レーダーが更新されたら、記録の下書きではなく「その出来事の画面」を作る
（ユーザー訂正 2026-11-07）。画面生成は次の分担で成り立つ:

- LLM が決めるのは **レイアウトと文章だけ**: 部品カタログからセクションの
  並びを選び、タイトル・要約文・見立てへの影響文を書く
- データは **コードが実データで埋める**（materialize）。LLM が数値や URL を
  画面に直接書くことはできない
- 描画は決定的な React コンポーネント。LLM が HTML を書く経路はない
- 生成された画面スペック（JSON）は D1 の `generated_views` に保存され、
  チャット欄にそのまま描画される

## 部品カタログ（`src/views.ts` の ViewSpec）

| セクション      | 描くもの                                                                           |
| --------------- | ---------------------------------------------------------------------------------- |
| `summary`       | 出来事の要約文（LLM の文章、ゲート通過分のみ素通し）                               |
| `assessment`    | 見立てへの影響（LLM の文章）+ baseline の抜粋（コードが付与）                      |
| `article_cards` | 記事カード列（タイトル・媒体・日時・国・トーン、出典リンク）。新しい順、最大 12 件 |
| `timeline`      | 時系列リスト。古い順、最大 20 件                                                   |
| `tone_chart`    | TanStack Charts: 日別件数バー + 平均トーン線                                       |
| `source_list`   | 媒体別の件数と代表記事リンク                                                       |
| `stat_row`      | 統計チップ（プール累計・frontier・直近 24h 件数・クラスタ件数）                    |

LLM の選択が壊れている（JSON 不正・未知の部品など）場合は、決定的な
フォールバック配置（`fallbackChoice`）で画面を作る。画面生成が「失敗して
何も出ない」ことはない。

## 検証ゲート（`verifyViewSpec`）

画面が保存される前に、次を機械的に検査する。不合格でも保存はするが
`verified = 0` と警告文を付け、UI に「要確認」と表示する:

- 記事カード / 時系列に載る記事 URL が、入力集合（そのクラスタの記事）に
  実在すること
- 出典リストの代表 URL が入力集合に実在すること
- タイトル・見出し・要約・見立て文に現れる URL が入力集合に実在すること
- 同じ文章群に現れる数値が、入力（記事タイトル・日時・件数など）に
  現れる数値の集合に含まれること

数値の許容集合は `allowedNumbersFor` が作る: 記事タイトルと seendate から
抽出した数値、記事件数、トレンドの日別件数・トーン（丸め違いを吸収する
ため整数化した値も含む）。

## チャットからの画面生成

`build_view` ツールが同じ経路を使う（origin は `chat`、自動生成は `cron`）。
プールの最新記事からクラスタを取り、決定的配置で画面を組み立てて保存し、
チャット欄に描画される。会話の文脈でキーワードを絞ることもできる。

## 空状態の扱い

ツールは例外を投げない。空プール・該当なしは「空の結果」を正常に返し、
UI は空状態の文言を出す。ツールが本当に失敗した場合は構造化された
穏当な文言（例: 「トーン推移を取得できませんでした」）を結果として返し、
生のエラーメッセージを画面に出さない（クライアント側も `output-error`
時は固定文言を表示する）。モデルのツール入力は緩く受ける（数値の文字列
渡し、問い ID の大文字などをサーバ側で正規化する）。
