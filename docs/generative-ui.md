# Generative UI の方式

## 原則

レーダーが更新されたら、記録の下書きではなく「その出来事の画面」を作る
（ユーザー訂正 2026-11-07）。画面生成は次の分担で成り立つ:

- LLM が決めるのは **レイアウトと文章だけ**: 部品カタログからセクションの
  並びを選び、タイトル・要約文・見立てへの影響文を書く
- データは **コードが実データで埋める**（materialize）。LLM が数値や URL を
  画面に直接書くことはできない
- 描画は決定的な React コンポーネント。LLM が HTML を書く経路はない
- 生成された画面スペック（JSON）は D1 の `generated_views` に保存され、
  チャットで生成したものは会話の中にそのまま描画される。自動生成分は
  サイドバーの折りたたみから開いたときだけオーバーレイで描画される

## 部品カタログ（`src/views.ts` の ViewSpec）

| セクション      | 描くもの                                                                           |
| --------------- | ---------------------------------------------------------------------------------- |
| `summary`       | 出来事の要約文（LLM の文章、ゲート通過分のみ素通し）                               |
| `assessment`    | 見立てへの影響（LLM の文章）+ baseline の抜粋（コードが付与）                      |
| `article_cards` | 記事カード列（タイトル・媒体・日時・国・トーン、出典リンク）。新しい順、最大 12 件 |
| `timeline`      | 時系列リスト。古い順、最大 20 件                                                   |
| `tone_chart`    | TanStack Charts: 日別件数バー + 平均トーン線                                       |
| `source_list`   | 媒体別の件数と代表記事リンク                                                       |
| `stat_row`      | 統計チップ（プール累計・frontier・直近 24h 件数・クラスタ件数）                    |

LLM の選択が壊れている（JSON 不正・未知の部品など）場合は、決定的な
フォールバック配置（`fallbackChoice`）で画面を作る。画面生成が「失敗して
何も出ない」ことはない。

## 検証ゲート（`verifyViewSpec`）

画面が保存される前に、次を機械的に検査する。不合格でも保存はするが
`verified = 0` と警告文を付け、UI に「要確認」と表示する:

- 記事カード / 時系列に載る記事 URL が、入力集合（そのクラスタの記事）に
  実在すること
- 出典リストの代表 URL が入力集合に実在すること
- タイトル・見出し・要約・見立て文に現れる URL が入力集合に実在すること
- 同じ文章群に現れる数値が、入力（記事タイトル・日時・件数など）に
  現れる数値の集合に含まれること

数値の許容集合は `allowedNumbersFor` が作る: 記事タイトルと seendate から
抽出した数値、記事件数、トレンドの日別件数・トーン（丸め違いを吸収する
ため整数化した値も含む）。

## チャットからの画面生成

`build_view` ツールが同じ経路を使う（origin は `chat`、自動生成は `cron`）。
プールの最新記事からクラスタを取り、決定的配置で画面を組み立てて保存し、
チャット欄に描画される。会話の文脈でキーワードを絞ることもできる。

## UI 方針: チャット中心（2026-11-07 ユーザー決定）

画面は「よくある AI チャット」の形に統一した:

- **初期状態の表示要素は、チャット入力欄とスレッド一覧のみ。** 候補
  チップ・候補カード・おすすめ・例文ヒントを含め、一切のコンテンツを
  聞かれる前に出さない。鮮度ボード・neurons メーター・生成画面フィード
  の常設パネルも置かない
- 画面（部品）は質問への回答としてのみ、会話の中に生成・表示する
- ツール実行ステップの詳細・ツール入力・生エラーは表示しない。表示する
  のはツールの出力（＝回答の部品）だけ。失敗時は固定の穏当な文言のみ
- Cron の自動生成画面は内部動作として残すが、トップ画面に常設しない。
  サイドバー下部の折りたたみ（既定は閉）から開いたときだけ、読み取り
  専用オーバーレイ（`<dialog>`）で見える

## 注目度ランキング（「いま世界情勢で何が注目されているか」）

利用者の関心は「収集プールの操作」ではなく「いま世界情勢で何が注目
されているか」。漠然と聞かれた場合（例:「いま何が注目されてる？」）は
`hot_events` ツールが注目度順の出来事一覧を回答として出す。

- 候補の組み立て（`hotEvents`、src/generate.ts）: 問いごとにプールの
  最新 150 件を取り、既存の決定的クラスタリングで出来事に畳む。
  2 件以上のクラスタだけを候補にする（単独記事は出来事とみなさない）
- 順位付け（`rankEvents`、src/logic.ts）: **LLM 任せにしない決定的
  ランキング**。キーは (1) 報道量 = クラスタの記事件数（多い順）、
  (2) 媒体数 = 報じたドメインの種類数、(3) 新しさ = クラスタ内の
  最新記事日時、(4) 問い ID、(5) クラスタキー。同点まで含めて完全に
  決定的で、同じプールからは常に同じ順序になる
- 各出来事には「6つの問いのどれか」のタグ（問い ID とラベル）を付ける
- 期間の正直さ: プールは 8 月のバックフィル中心なので、回答には
  対象期間としてプール全体の最新 frontier（`poolLatest`）を明示し、
  架空の「現在」を装わない
- 出来事の画面は、回答内の「画面を見る」ボタン経由
  （`POST /api/threads/:id/event-view`）でのみ生成される。チャットの
  モデルは出来事の画面を生成するツールを持たない（ツール定義の層で
  抑止）。これは、ツールがあった頃にモデルがランキング回答の直後へ
  例として1件選んで画面まで自動生成してしまった実測を受けた対策で、
  ランキング回答は出来事の提示だけに留まる
- ボタン経由の生成では、その出来事の画面がそのスレッド内に案内役の
  メッセージとして追記される。利用者発言風の合成メッセージは作らない
  （履歴に本人が書いていない発言を増やさない）。生成は決定的配置＋
  検証ゲートの経路（`buildEventView`）を通る

## スレッド管理

- スレッド = ExplorerAgent の DO インスタンス（DO 名 = スレッド ID）。
  会話履歴は DO の SQLite にスレッドごとに保持される
- D1 の `threads` テーブルは一覧表示用の索引（ID・タイトル・作成/更新
  日時）だけを持つ。タイトルは最初のユーザ発言から自動で付ける
- API: `GET /api/threads`（一覧。初回は従来の単一会話 `main` を
  「これまでの会話」として種まきし、履歴を失わない）、
  `POST /api/threads`（新規作成）
- 切り替えはクライアントが Agent 名を替えて再接続し、そのスレッドの
  履歴を読み直すことで行う（ChatPanel をスレッド ID で keyed remount）
- スレッドの削除 UI は持たない（作成・一覧・切り替え・再開のみ）

## 空状態の扱い

ツールは例外を投げない。空プール・該当なしは「空の結果」を正常に返し、
UI は空状態の文言を出す。ツールが本当に失敗した場合は構造化された
穏当な文言（例: 「トーン推移を取得できませんでした」）を結果として返し、
生のエラーメッセージを画面に出さない（クライアント側も `output-error`
時は固定文言を表示する）。モデルのツール入力は緩く受ける（数値の文字列
渡し、問い ID の大文字などをサーバ側で正規化する）。
